# Python 3.11 support (PR #4) — measured consequences of dropping PEP 695

Investigated 2026-07-25 (Matthew + Claude) while reviewing PR #4 from
Zhi-Yi Chin, which replaces the nine `type X = ...` aliases in
`colormaps.py`, `colors.py` and `data.py` with `TypeAlias` assignments.

## The bug the PR is right about

`pyproject.toml` says `requires-python = ">=3.10"` and that is **false**.
PEP 695's `type` statement is 3.12+, so the package cannot even be parsed
below 3.12:

    ast.parse(colors.py, feature_version=(3,11))
    -> SyntaxError: Type statement is only supported in Python 3.12 and greater

pip will therefore install happily on 3.10/3.11 and the import then explodes.
Something has to change here regardless of which option below is chosen.

Note `typing.Self` (used in `core.py` and `plots.py`) is **3.11+**, so 3.10
cannot work whatever we do with the aliases. The real choice is 3.11 or 3.12.

## What the PR costs, measured

Docs are generated by pdoc from the *runtime* alias values, so how the aliases
are spelled shows up directly in the published API reference.

Rendered `matthewplotlib.data`, on main:

    type number = int | float | numpy.integer | numpy.floating
    type ColorSpec = None | ColorLike | ArrayLike

and with PR #4:

    number: TypeAlias = Union[int, float, ForwardRef('np.integer'), ForwardRef('np.floating')]
    ColorSpec: TypeAlias = Union[NoneType, str, NDArray, ForwardRef('tuple[int, int, int]'),
                                 ForwardRef('tuple[float, float, float]'), ArrayLike]

Three separate degradations, of which only two are avoidable:

1. **`ForwardRef('...')` noise — avoidable.** Most of the PR's quoting is
   unnecessary. `tuple[int, int, int]` is valid at runtime from 3.9 (PEP 585)
   and `np.integer` is already imported. Only `axis` in `data.py` is a genuine
   forward reference, because it is defined below the aliases.
2. **`Union[...]`/`NoneType` instead of `|` — avoidable.** PEP 604 `X | Y`
   works at runtime from 3.10, including for `NDArray` and `tuple[...]`. The
   rewrite to `Union[]` is not needed. Caveat: you cannot `|` a string, so an
   alias with a quoted member is forced back to `Union[]` —
   `"axis" | tuple[int, int]` raises TypeError. That is why `Series`/`Series3`
   specifically would need `Union[]` unless `axis` moves above them.
3. **Nested alias names are lost — NOT avoidable.** `ColorSpec` no longer
   mentions `ColorLike`; it gets expanded into its members. This is inherent
   to eager evaluation, not to quoting or to `Union[]`:

       Spec: TypeAlias = Union[None, ColorLike, float]  -> Union[NoneType, str, int, float]
       Spec: TypeAlias = None | ColorLike | float       -> Union[NoneType, str, int, float]
       type Spec        = None | ColorLike | float       -> None | ColorLike | float

   PEP 695 aliases are lazy, so `__value__` still holds the reference. Nothing
   eager can preserve it. `ColorSpec` and `Series`/`Series3` are the affected
   aliases.

Nothing in the library introspects these aliases at runtime (no
`get_type_hints`, `get_args`, `get_origin`, `__value__`, and no `isinstance`
against them), so eager vs lazy has **no** behavioural consequence. The whole
question is documentation quality versus interpreter reach.

## Options

- **(a) Merge PR as submitted.** 3.11 works; all three degradations; also adds
  an *undeclared* dependency on `typing_extensions` (not in `pyproject.toml` —
  it only imports locally because a dev dependency pulls it in, so a fresh
  install of the library would break). `typing.TypeAlias` exists from 3.10 and
  needs no dependency, so this part is simply a mistake.
- **(b) `typing.TypeAlias`, keep `|`, quote only `axis`.** 3.11 works; no
  ForwardRef noise except `axis`; `Series`/`Series3` still forced to `Union[]`;
  nested names still lost.
- **(c) As (b), plus move `axis` above the alias block.** 3.11 works; zero
  quotes; every alias keeps `|`; nested names still lost. Costs a restructure
  of `data.py`'s `# # #` fold sections (`axis` only depends on `number`, so the
  reorder is otherwise free).
- **(d) Keep PEP 695, set `requires-python = ">=3.12"`.** No 3.11 support;
  docs unchanged; zero code change. Fixes the actual lie in the metadata.

## Where this was left

Deferred out of the 0.4.0 sprint, as it needs a judgement call rather than a
fix: is 3.11 reach worth a permanent documentation regression? 3.11 is
supported upstream until Oct 2027 and is what many conda/HPC environments
still run, so the reach is real.

If the answer is yes, (c) is the version to accept, and Zhi-Yi should get the
reasoning above rather than a silent rewrite. If no, (d) is a one-line change.
